# Heofberu UI design-sync notes

## Repo shape

`src/components/ui` (`primitives.jsx` + `ThemeSwitcher.jsx`, plain JS/JSX — no TypeScript, no Storybook, no standalone package/dist) is a small shared-primitives folder inside the `heofberu-frontend` app, not a published component library. The sync now also mirrors a handful of full **pages** (see "Page-level compositions" below) — the rest of the app's `src/features/**` tree is still out of scope.

## Page-level compositions (`.design-sync/pages/*.jsx`)

Beyond the `src/components/ui` primitives, this sync mirrors these real pages as **reference compositions** — new files in `.design-sync/pages/` that import and render the REAL page/panel components (never reimplemented), wrapped with a local `QueryClient` (pre-seeded to match the exact React Query cache keys those components read) instead of a live backend:

- `CharacterSheetPage.jsx` → the character detail page (`src/features/characters/pages/CharacterDetailPage.jsx`), all 9 content tabs, `initialTab` prop.
- `AuthPages.jsx` → thin wrappers around the real `LoginPage`/`RegisterPage`/`ForgotPasswordPage`/`ResetPasswordPage` (these needed no mock composition — just Router + auth context, since they're already fully self-contained forms).
- `CharactersPage.jsx` → the character list (landing page after login).
- `CharacterCreatePage.jsx` → the character-creation wizard, all 8 steps, `initialStep` prop.
- `CatalogPage.jsx` → the catalog browse/detail page, **all 8 resources seeded** (races, classes, skills, spells, backgrounds, feats, items, features) — each renders through its own real `DetailPanel` sub-component dispatch (`RaceDetailCard`/`ClassDetailCard`/`SpellDetailCard`/`BackgroundDetailCard`/`FeatDetailCard`/`ItemDetailCard`/`FeatureDetailCard`, or `GenericDetail` for skills), since these cards differ meaningfully in layout and fields (subrace/subclass lists, fact-row sets, ability-increase badges, etc). One `List` story (browse grid) plus one `Detail` story per resource.
- `SheetModals.jsx` (expanded) → beyond the 5 `Modal`-shell dialogs, now also covers the pickers `CharacterSettingsModal` opens (`SubracePickerModal`, `SubclassPickerModal`, `BackgroundPickerModal`), the `AttackModal`/`SpellPickerModal` reached from the Attacks/Spells tabs, and `AsiChoiceModal` (the ASI-vs-feat level-up dialog — its own bespoke fixed-overlay, not the shared `Modal`). 11 `which` values total.
- `CatalogModals.jsx` → the catalog's own dialogs: `FilterModal` (browse pill-filters), `ItemInfoModal` (full item detail popup), the GM editor's `FeatureModal` (create/edit, ability-increase row builder) and `ItemPickerModal` (search/filter/paginate a selection list, with an optional "choose N of" group builder for class starting-equipment).
- `UsersPage.jsx` → admin user-management table.
- `GmCharactersPage.jsx` → GM's character roster + the full `GmCharacterPanel` (6 sections: level, HP/rest, skills/expertise, feats, features, stats, items) — reconstructed shell (the real page's selection state is internal with no controlling prop, same reason as `CharacterCreatePage`), reusing the real `GmCharacterPanel` verbatim.
- `GmEditorPage.jsx` → the GM catalog editor (1586 lines, the largest page in the app), **scoped to the `'races' resource only** (the real page supports classes/skills/spells/backgrounds/feats/items/features too, each with different `editorConfig` section types — `spellSlots`/`spellcasting` for classes, plain `rows`/`pillsFrom` for races). Reuses the REAL `editorConfig.races` (fields/sections/listBadges/fromRecord are pure functions — genuinely imported, not reimplemented) and the real editor sub-components (`EditorFieldControl`, `FeaturesEditorBlock`, `RecordListItem`, `SubraceEditor`); only the outer state machine (which is entirely local/imperative in the real page, no React Query at all) is reconstructed with mock records standing in for `api.races.*` calls.
- `SheetSidebar.jsx` → the character sheet's ability-score `<aside>`, exposed as its OWN standalone component (in addition to being embedded inside `CharacterSheetPage.jsx`) since on desktop it's a persistent independent panel, not something that only makes sense nested in the full page. Duplicates a slice of `CharacterSheetPage.jsx`'s derived-value logic (totals/skillsByAbility/passiveSenses/etc) around real `AbilityBlock`/`PassiveSenses`/`ProficiencyList` components — see the "page compositions can drift" risk note below, now doubly true since this logic now exists in two files.
- `SheetModals.jsx` → the character sheet's own dialogs: `HpModal`, `ArmorModal`, `MoneyModal`, `LevelUpModal`, `CharacterSettingsModal` (all real, unmodified), picked one at a time via a `which` prop, over a shared mock character + a QueryClient seeded with `classDetail`/`backgroundDetail`/subrace-and-subclass-lists/feats (needed by `LevelUpModal`'s ASI flow and `CharacterSettingsModal`'s picker tiles). **Out of scope**: the pickers `CharacterSettingsModal` opens (`SubracePickerModal`/`SubclassPickerModal`/`BackgroundPickerModal`/`AsiChoiceModal`) are real components too and will actually work if clicked into (the seeded cache covers them) but aren't separately previewed; `AttackModal`/`SpellPickerModal` (nested inside `AttacksPanel`/`SpellsPanel`) weren't read or covered at all this round.
- `AppShell.jsx` → the app's global chrome (`src/components/layout/Layout.jsx`): sticky header + desktop fixed sidebar (expanded/collapsed) + mobile full-screen nav overlay, reconstructed (real page reads `useAuth()`/`<Outlet/>`, can't render standalone) with `authenticated`/`isGM`/`initialCollapsed`/`initialSidebarOpen`/`children` props. **Split into two exported components — `AppShell` (desktop stories, wide viewport) and `AppShellMobile` (phone-width stories, same underlying `Shell`)** — purely a capture-viewport workaround: this converter's `cfg.overrides.<Name>.viewport` is per-*component*, not per-story, and the desktop fixed-sidebar layout and the mobile hamburger-overlay layout need viewports on opposite sides of the `lg:` (1024px) breakpoint to render correctly, so one component can't host both.

**Why query-cache seeding, not mocked API modules:** every one of these pages/panels reads data via React Query hooks bound to fixed, derivable query keys (`queryKeys.characters.attacks(id)`, `['catalog','classes','page',params]`, etc). Since the app's global `QueryClient` default `staleTime` is 60s, calling `queryClient.setQueryData(exactKey, mockData)` before first render means the component reads the seed synchronously with no network call in the render window — no need to fork `api.js`/`queries.js` or touch axios/httpClient at all. A background refetch may still fire and fail silently against no backend (harmless — the seeded data stays until it succeeds or the viewer navigates away).

**Two real bugs hit while authoring these — both are lessons about query-key/data-shape precision, not converter bugs:**
1. **Combined-array group indices.** `StepEquipment`/`StepSummary` (character-creation wizard) build the choice-group key as `` `${source}:${gi}` `` where `gi` is the index in the **combined** `[...classGroups, ...backgroundGroups]` array, not a per-source index — so with one group each, the background group is `'background:1'`, not `'background:0'`. Always read the actual indexing logic in the component, don't assume per-source indices.
2. **List entries and detail objects are different response shapes.** A field present on a catalog list entry (e.g. `hit_dice` on the `classes` list tile) is NOT automatically present on that same entity's *detail* object (`classDetail`) — the real backend returns them as separate response shapes, and several step/detail components read fields (`.name`, `.hit_dice`) directly off the **detail** object, not the list entry. When mocking, put every field the detail-consuming component reads on the detail mock too, even if it looks redundant with the list mock.

**`componentSrcMap` trap:** adding explicit `componentSrcMap` entries (even just for grouping — pinning a component's `srcPath` to control which folder/group it lands in) populates the converter's component name-list directly. Since the synth-entry auto-discovery fallback (`deriveComponentsFromSrc`, which scans every `.jsx` file in the package root for exported PascalCase names) only runs when that name-list is **completely empty**, adding even one `componentSrcMap` entry silently disables auto-discovery for every *other* component in the package — they vanish from the build with no error. Learned this the hard way trying to fix `LoginPage`/etc.'s group; reverted immediately. If a component's auto-derived group is wrong, live with it (or move the file into a real subdirectory) rather than reaching for `componentSrcMap` to fix grouping alone.

**`lg:` responsive breakpoints collapse in `cardMode: "column"`.** The default column-mode render viewport is narrower than Tailwind's `lg` (1024px) breakpoint, so any page whose desktop layout is gated behind `lg:` (e.g. `CatalogPage`'s two-column `catalog-layout` grid, which hides all but the active item below `lg:`) renders its **mobile** layout instead. Fix: add an explicit `cfg.overrides.<Name>.viewport` wide enough to clear the breakpoint (`CatalogPage` uses `"1280x900"`) even though `cardMode` stays `"column"`.

## Build setup (why `cfg.buildCmd` looks the way it does)

The package-shape converter needs a `node_modules/<pkg>` directory to resolve as the "package" — since this repo has no such package, `buildCmd` creates a scratch one at `node_modules/heofberu-ui/` (gitignored, ephemeral, recreated by the command every time):
- Copies the two source files in as-is (no build step exists for them — the converter runs in synth-entry mode, scanning the `.jsx` files directly for PascalCase exports).
- Copies in a `tsconfig.json` (source lives at `.design-sync/build.tsconfig.json`, committed) so esbuild's path-alias plugin can resolve `@/lib/theme.js`-style imports from `ThemeSwitcher.jsx`.
- Copies in a `package.json` stub (`dts.mjs`'s `projectFor` reads it unconditionally).
- Copies the Tailwind-compiled CSS from `npm run build`'s `dist/assets/index-*.css` output to `styles.css`, since Tailwind v4 only emits real (non-`@apply`) CSS after a full app build — `cfg.cssEntry` must point at compiled CSS, not the `@import "tailwindcss"` source file.

## Decisions made this sync

- **`ThemeSwitcher` excluded** (`componentSrcMap: {"ThemeSwitcher": null}`). It's `export default function ThemeSwitcher()` — synth-entry mode emits `export * from` for each source file, which does NOT re-export a default-only export, so it never lands on `window.HeofberuUI`. It's also a thin, app-specific toggle hardcoded to this app's `light`/`parchment` theme ids and `@/lib/theme.js` — not a generic reusable primitive, so exclusion is the right call, not just a workaround.
- **Font substitute accepted** (user confirmed). `--font-display` is a system-font stack (`"Palatino Linotype", "Book Antiqua", "Palatino", Georgia, "Times New Roman", serif`) with no shipped webfont — intentional, not a missing asset. Designs render it via whatever serif the viewer's OS provides.
- **`dtsPropsFor` hand-written for all 24 components.** Since the source is plain JS (no `.d.ts` anywhere), the converter's default synth-entry path produces empty/weak prop contracts. Prop shapes in `.design-sync/config.json` were transcribed from reading `primitives.jsx` directly — accurate as of this sync, but not compiler-verified, so a future signature change in `primitives.jsx` won't automatically invalidate the config's copy.
- **No provider needed.** Nothing in this component set reads from React context; styling comes entirely from Tailwind classes/tokens and CSS custom properties.

## Re-sync risks (read before the next sync)

- **The dark-background requirement is the single most important fact about this DS** — see `.design-sync/conventions.md`. If it's ever rewritten, keep that warning: components use light text tones calibrated for a dark ground and are unreadable on white.
- **`dtsPropsFor` can drift.** If `primitives.jsx` changes a component's props, `.design-sync/config.json`'s hand-written contract for that component needs a matching edit — nothing will flag the mismatch automatically.
- **`Chip` renders no text color of its own** (`.badge-row` is layout-only). Its authored preview (`.design-sync/previews/Chip.tsx`) sets `text-sm text-stone-300` on the wrapper to compensate, matching how `detailHelpers.jsx` uses it in the real app (inside an ancestor that supplies text color). Any new Chip story needs the same treatment or it'll render invisible.
- **`Modal`/`ConfirmDialog` use `cfg.overrides.<Name>.viewport`** (`640x420` / `480x320`) tuned by eyeballing the rendered dialogs — if their content grows meaningfully, the viewport may need widening/heightening again (watch for a dialog with its title clipped off the top of the card).
- **No Storybook** — every preview is hand-authored under `.design-sync/previews/`. Any component added to `src/components/ui` in the future ships with a floor card until someone writes and grades a preview for it.
- **`styles.css` comes from a full `npm run build` of the whole app**, not a component-scoped build — it will always include Tailwind classes used anywhere in the app, not just in `src/components/ui`. Harmless (just non-minimal), but means the shipped CSS is larger than the strict minimum for these components.
- **Page compositions can silently drift from the real pages.** `.design-sync/pages/*.jsx` reconstruct each page's outer state/derived-value logic (mock catalog data, mock character, `initialTab`/`initialStep`/`path` props) around the REAL inner components — if the real page changes its prop names, its derived-value formulas (e.g. `CharacterDetailPage`'s `totals`/`skillsByAbility`/`passiveSenses` logic, copied into `CharacterSheetPage.jsx`), or a step/panel's query key, the composition can go stale with no automatic warning (unlike `dtsPropsFor`, there's no drift detector for these). Re-diff the relevant real page against its `.design-sync/pages/*.jsx` counterpart whenever that page's own source changes meaningfully.
- **`CatalogPage.jsx` only mocks the `'classes'` resource.** Extending it to another resource (races, spells, items, feats, backgrounds, features, skills) means reading that resource's own `DetailPanel` card component and building a matching mock detail object — the `'classes'` mock is a template for the *pattern*, not a generic solution.
- **`node_modules/heofberu-ui/` is fully ephemeral** — every file placed there via `buildCmd` (including everything under `pages/`) is gitignored and recreated from `.design-sync/pages/*.jsx`/`.design-sync/build.tsconfig.json` on every build. Never hand-edit anything inside `node_modules/heofberu-ui/`; edit the `.design-sync/` source and re-run `buildCmd`.
- **`resync.mjs` does NOT run `cfg.buildCmd` itself.** It only scans whatever is already sitting in `node_modules/heofberu-ui/` — after adding/editing any `.design-sync/pages/*.jsx` file, run the full `buildCmd` shell command by hand first (or the driver will silently synthesize from the STALE file set with no error, just a lower "synthesizing from N src files" count than expected — that's the tell something didn't get copied).
- **Components with `fixed`/`position`-escaping content (portals, `position: fixed` overlays, sticky headers spanning the viewport) trip `[GRID_OVERFLOW]` even under `cardMode: "column"`.** `AppShell`/`AppShellMobile` (fixed sidebar, fixed full-screen mobile menu) needed `cardMode: "single"` + an explicit `primaryStory` instead — per the tool's own guidance, single-card mode is exempt from the grid-cell-containment check by construction. All other stories still exist and render (see their own screenshots during grading), just the multi-story contact-sheet card shows one representative story.
- **A `cardMode: "single"` story's outer wrapper div needs `height: '100vh'`, not `minHeight`.** The single-card HTML harness mounts each story inside a `.ds-single` div with `transform: translateZ(0)` on it (and on `.ds-cell`) — applying a CSS `transform` to an ancestor makes it the containing block for any `position: fixed` descendant (a CSS rule, not a converter bug). Every real `Modal`/`AsiChoiceModal` overlay uses `fixed inset-0`, so it ends up sized/centered against the STORY WRAPPER's box, not the true browser viewport — and that wrapper's height is just its content's normal-flow height (since `fixed` children contribute ~0 to it). A composition root div with `minHeight: 480` silently caps every fixed-overlay dialog inside it to ~480px tall regardless of `cfg.overrides.<Name>.viewport`, clipping anything taller (hit this with `AttackModal` and `AsiChoiceModal` in `SheetModals.jsx` — both rendered with their top AND bottom cut off at the exact same pixel offset no matter how large the configured viewport got, which was the tell). Fix: give the composition's root wrapper `height: '100vh'` — `vh` units resolve against the real viewport regardless of ancestor transforms, so the wrapper (and therefore the fixed overlay's containing block) always matches the configured capture viewport.
- **A single component's capture `viewport` can't span both sides of a responsive breakpoint.** `AppShell`'s desktop stories need `>=1024px` width to show the fixed sidebar column; a "mobile menu open" story needs `<1024px` so the `lg:hidden` overlay isn't hidden by its own class. Since `cfg.overrides.<Name>.viewport` is per-component, this needed splitting into two exported components (`AppShell` wide-viewport, `AppShellMobile` phone-viewport) sharing one internal implementation, rather than one component with stories at both widths.
